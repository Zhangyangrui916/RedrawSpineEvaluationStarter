# 从一个换皮工具，到一道 Code Agent 测评题

---

## 一、原来的工程在解决什么问题

### 先说 Spine 是什么

Spine 是 2D 骨骼动画的行业标准工具。一个角色在 Spine 里不是一张图，而是被拆成很多**部件**——左手、右手、头、上衣、裙子、剑，每个部件是一张独立的 PNG。这些部件挂在骨骼上，骨骼做动画，部件就跟着动。

一个中等复杂度的角色大概有二十到两百张部件图。文件上它们叫 attachment，每张图对应图集（atlas）里的一个区域。

### 换皮为什么难

给角色做一套新衣服，意味着要重画这些部件图。听起来只是美术工作量，但真正麻烦的地方在于：**部件图是彼此孤立的**。

画师面对的是一张"右手_张开朝内.png"，一张"裙子_下摆.png"。他看不到这些东西拼起来是什么样，也看不到袖口和手腕在动作中怎么衔接。等到导回引擎里播动画，才发现接缝对不上、光影方向不一致、袖子的花纹在手抬起来时断掉了。然后回去改，再导，再看。

**画师需要看着"角色"作画，但工具只允许他看着"零件"作画。**

### RedrawSpine 的思路

那就反过来做：

1. 把角色摆一个姿势，**渲染成一张完整的图**——这时候它是一个人，不是一堆零件；
2. 在这张完整的图上重绘（原工程用的是 Stable Diffusion + ControlNet，也可以是人手画）；
3. 把重绘后的像素**映射回各个部件图**上去；
4. 换一个姿势，重复——因为一个姿势看不到全身，手会挡住腰，正面看不到背面。

第 3 步是整个工具的技术核心，也是唯一一个"没有现成方案"的地方。前两步是渲染和调 API，第 4 步是循环。而第 3 步要回答的是：

> 屏幕上这个像素，来自**哪一张部件图**的**哪一个像素**？

这是一次**反投影**。正向渲染是"部件图 → 骨骼变换 → 屏幕"，现在要把它倒过来走。原工程的做法是在渲染时额外输出一张整数缓冲，每个屏幕像素里编码了 `(部件编号 << 24) | 该部件图内的线性下标`，读回来之后就能把颜色写回去。

### 原工程还处理了两个现实问题

**看不见的地方怎么办。** 一次渲染只能覆盖角色的一部分，多个姿势叠起来也总有死角——腋下、重叠处、从来没转过身的背面。原工程的做法是：先按姿势顺序写，同一个像素只写第一次（first-write-wins），最后对剩下的空洞做邻域扩散填充（flood fill），让最终的部件图看起来是完整的一张新皮肤，而不是补丁。

**分辨率。** 渲染的画布大小直接取全动画包围盒的世界坐标尺寸，也就是 1 个世界单位 = 1 个屏幕像素。这样一个部件图上的一个像素，在屏幕上差不多也占一个像素，反投影时用最近邻取整就够了，误差最多半个像素，肉眼不可见。

## 二、为什么这个工程适合改成 Code Agent 的测评题

任务手册里对好测例的要求是：是 Agent 任务、有区分度、真实、可验证。这个工程恰好在四条上都成立，而且是**同一个原因**造成的——它的核心是一个必须自己推导的几何问题，而不是一个能背下来的 API 调用序列。

具体来说：

**它必须读别人的代码。** Spine 的骨骼变换、蒙皮网格、绘制顺序都在官方 runtime 里。候选人不可能凭空写出来，必须去读 `spine-cpp`，找到 `computeWorldVertices`、`updateWorldTransform` 这些入口，理解它们的语义。这是真实的"进入陌生代码库"的能力。

**它必须搭环境、跑起来、自己验证。** 光想是不行的：要配 CMake、编译第三方库、处理无显卡容器里的离屏渲染，然后跑出结果看对不对。而且——这一点后面会详细说——它必须自己造一个验证手段，因为工作区里没有任何东西会告诉你"你做对了没有"。

**它的正确性可以被机器判定。** 输出是一组固定名字、固定尺寸的 PNG。把它们装回骨骼，渲染一些候选人没见过的姿势，和标准答案逐像素比——这个流程完全确定，不需要人来判断。

**它是真的需求。** 不是为了出题编的场景。

---

## 三、从生产工具到测评题，改了什么

这一节是主要内容。每一项都是一个具体的取舍，而不是简单的裁剪。

### 3.1 把 Stable Diffusion 拿掉

原工程靠 SD 生成新皮肤。作为测评题这不行：SD 有随机性、要显卡、要联网，而且它生成什么内容不可控——同一个模型跑两次，题目难度就不一样了。

替换方案是：**预先合成一套确定的目标皮肤 S1**，然后给候选人若干组"同一姿势下的两张渲染图"：

```
before.png  = 用原皮肤 S0 渲染
after.png   = 用目标皮肤 S1 渲染（S1 候选人看不到）
```

任务从"重绘"变成了"**从这些成对的渲染图里，把那套看不见的皮肤还原出来**"。数学上是同一个反投影问题，但现在有唯一答案，可以机器判分。

这一步顺带解决了原工程的另一个问题：SD 每一帧的输出未必自洽，同一个部件在不同姿势下可能被画成不同颜色，反写回去就会冲突。而合成的 S1 是一套固定的贴图，天然自洽，于是"多个观测之间有没有矛盾"这个噪声源被去掉了，剩下的误差全部来自候选人的实现。

### 3.2 把迭代流程压成一次性任务

原工程是个循环：渲染一帧 → SD 重绘 → 写回贴图 → 用更新后的贴图渲染下一帧。后面的帧依赖前面的结果。

测评平台是**单轮无上下文**的——模型看不到之前的对话，任务必须自包含。所以所有观测一次性给全，并且明确说明**观测之间没有处理顺序语义**。

这不只是迁就平台。它还有两个好处：一是去掉了路径依赖，不同次运行之间可比；二是把题目从"实现一个流水线"变成了"求解一个方程组"，考的东西更纯粹。

### 3.3 判分必须和候选人的代码彻底隔离

题目明确允许候选人改渲染器、改 shader、改构建、甚至改动 Spine 集成方式。那判分就绝对不能复用候选人碰过的任何东西——否则一个把渲染器改坏的候选人，可能因为"判分也用了同一个坏渲染器"而恰好通过。

所以判分侧有一套**独立的可信渲染器**，和候选人的代码零共享。判分时：

1. 只读候选人产出的那 20 张 PNG，其他一概不看；
2. 用**原始的**骨骼、图集、动画，把这些 PNG 装回去；
3. 渲染一批候选人从未见过的姿势；
4. 和用真实 S1 渲染的参考帧逐像素比。

这里有个容易走错的地方：**判分应该在渲染空间做，而不是在贴图空间做。** 直接比"候选人的 PNG 和真实 S1 的 PNG 差多少"看起来更直接，但那是错的——观测数据本来就不足以唯一确定每一个贴图像素，纠结单个像素等于在惩罚一个信息论上无解的问题。真正要问的是：**把这套贴图装回角色，动起来看，对不对。**

### 3.4 看不见的地方算谁的

这一项改了最多次，也是整道题里最有意思的部分。

原工程的语义是：SD 只重绘看得见的部分，看不见的地方保留旧皮肤，最后 flood fill 补洞让成品完整。

第一版测评照搬了这个语义，并且做得更严格：**目标皮肤 S1 在"所有观测都没覆盖到的地方"直接等于 S0**。这样判分极其简单——直接整帧比较，不需要判断每个像素依赖哪些贴图像素、有没有被遮挡、双线性采样跨了几个像素。

然后在试做中发现了问题。

一个实现得相当完整的 agent（细节见第五节）在这一版上拿了 0.78，没通过。它的反投影是**逐像素精确**的，但它默认"整套皮肤都被换了"，于是用平滑先验把重建出的颜色扩散到了整张贴图——包括那些它其实没有任何观测证据的区域。而那些地方的正确答案是"保持原样"。

这暴露了一个设计问题：**这条规则在题面里没有写，也没法从别处推出来。** 而且更重要的是——**按生产标准，这个 agent 的行为是对的。** 把空洞补上、让最终资产可以直接入库，正是原工程 flood fill 在做的事。把它判成错误，等于说原工程是错的。

所以规则改了。现在判分时会**先用可信渲染器算出一张"公开观测确实覆盖到了哪些贴图像素"的掩码，把掩码外的区域在一份临时副本里恢复成 S0，再拿去渲染打分**。候选人提交的文件不会被修改。

效果是：

- 候选人可以自由 flood fill、inpaint、或者干脆留着原皮肤，**都不影响分数**；
- 有证据的地方仍然被严格评价；
- 没证据的地方不再有一个候选人猜不到的"标准答案"。

### 3.5 分辨率

第一版把观测图渲染在 768×596，而世界坐标包围盒是 2450×1900——相当于缩小了 3.19 倍。这是为了省体积和时间。

代价没有被预料到。一个屏幕像素跨了 3.2 个贴图像素，而双线性采样一次只碰 2×2 个，于是**相邻采样之间会规律性地漏掉像素**。把覆盖掩码打印出来是这样的：

```
#####..##.##.##..######.##.####################.##.##...........
##########################.##....##.##..########################
##########.##############.#####.#######.##.##.##.###############
```

这不是遮挡造成的盲区，是采样栅格造成的伪影。它有两个后果：一是生成出来的 S1 变成了新旧皮肤的条带拼接，作为一张"新皮肤"根本不成立；二是整整三分之一的画面坐在这条锯齿边界上，既不算"该重绘"也不算"该保留"。

实测了几档分辨率之后（数据在第五节），改回了原工程的 1 世界单位 = 1 像素，也就是 2450×1900。条带消失，覆盖区变成连续的形状，剩下的盲区是真正的遮挡。

代价比预想的小：候选人的重建耗时只从 8 秒涨到 17 秒——因为 1:1 时方程组条件数好得多，迭代求解器提前收敛，抵消了十倍的数据量。

## 四、题目最终的样子

**给候选人的：**

- 官方 `spine-cpp` 源码、一个能跑的离屏渲染器、CMake 工程；
- 两个 case，每个含一套骨骼与图集、20 张原皮肤部件图、6~7 组 `(before, after)` 观测；
- 一个额外的**公开练习 case**，连答案一起给——包括目标皮肤和验证用的参考帧。候选人可以在上面无限次自测；正式的两个 case 用不同的种子生成，答案不公开，也没有可反复查询的分数。

**要交的：**

```bash
./build/redrawspine-reconstruct --case <case_dir> --output <output_dir>
```

产出 20 张 PNG，文件名和尺寸必须与 `case.json` 一致，alpha 通道必须与原图逐字节相同，RGB 应当不同。

**怎么判：**

对每个隐藏姿势，

```
候选人误差 = 平均|候选帧 - 参考帧| / 255
基线误差   = 平均|原皮肤帧 - 参考帧| / 255
本帧质量   = clamp(1 - 候选人误差 / 基线误差, 0, 1)
```

case 分数 = `0.8 × 平均质量 + 0.2 × 最差 20% 帧的平均质量`，两个 case 取平均，`≥ 0.9` 算通过。

用最差 20% 加权，是为了防止"大部分姿势蒙对、个别姿势崩掉"被平均掉——一个真正正确的重建应该在所有姿势下都对。

## 五、怎么确认这道题是有效的

题目写完不等于题目成立。判断一道测评题好不好，只能靠**实际跑一遍并测量**。

采用的方法是：让一个没有设计上下文的 agent 盲做，然后用真实的判分脚本给它打分，再手工构造若干"部分正确"的变体，看分数能不能把它们分开。

### 试做结果

那个 agent 走的是纯 CPU 路线：用官方 runtime 摆好姿势拿到三角形，自己写光栅化，对每个像素算出它采样了哪张部件图的哪四个像素，把每个像素变成一个线性方程，按部件图聚成稀疏最小二乘求解。全程没用提供的 OpenGL 渲染器。

有一个细节值得单独说，因为它是这道题里最好的能力信号：

> **`before.png` 是候选人唯一的自校验手段。** 它是用**已知的**原皮肤渲染的。候选人可以用自己的管线跑一遍已知的 S0，要求逐像素复现 `before.png`——如果投影公式、Y 轴方向、像素中心偏移、绘制顺序有任何一处搞错，这个检查立刻就会失败。
>
> 实测结果：2,657,613 个采样像素中，**误差超过 ±1/255 的有 0 个**。反投影是精确的，不是近似的。
>
> 题面里没有提示这一点。要不要提示，是一个明确的取舍：不提示，它就能筛出"会主动构造验证手段"的 agent；提示了，就变成了送分。目前的版本选择了在题面里写明——因为一个连自己对不对都无从判断的开发过程，本身就不是好的工程实践，不应该被当成考点。

### 各种实现的实测分数

都用真实判分脚本跑出来的，环境用"真实 S1 → 1.0000"校准过。

**旧数据（3.19 倍欠采样，掩码外不中性化）：**

| 实现 | 分数 | 通过 |
|---|---|---|
| 真实 S1 | 1.0000 | 是 |
| 正确重建 | 0.9833 | 是 |
| 最近邻反写 + 补洞 | 0.9792 | 是 |
| **盲做 agent 的原始提交**（外推到无证据区域） | **0.7832** | **否** |
| 最近邻反写，不补洞 | 0.4444 | 否 |
| 原样拷贝原皮肤 | ~0 | 否 |

**新数据（1:1，掩码外中性化）：**

| 实现 | 分数 | 通过 |
|---|---|---|
| 正确重建 | 0.9929 | 是 |
| 外推到无证据区域 | 0.9929 | 是 |
| 最近邻反写，不补洞 | 0.9794 | 是 |
| 原样拷贝原皮肤 | ~0 | 否 |

### 这两张表说明了什么

好的一面：**题目是可解的，而且解法不唯一。** 最小二乘和最近邻反写差 0.004，说明判分只冻结最终行为，没有暗中要求某一种算法。这是当初的设计目标。

需要正视的一面：**改完之后，判别力塌掉了。**

新数据上唯一会失败的只剩"什么都不做"。之前那两个能拉开差距的失败模式都消失了，而且都是被**正确的**修改消掉的：

- 外推失败从 0.78 变成 0.9929——因为中性化让它不可见了。这个修改本身是对的（不该惩罚合理外推），但它同时也拿走了一个能力信号；
- 最近邻不补洞从 0.44 变成 0.9794——因为 1:1 下相邻采样的覆盖范围本就重叠，根本没有孔可以漏。这个修改本身也是对的（消除采样伪影），但同样带走了一个信号。

两处修改各自都正确，叠在一起把这道题变成了一个**近乎二值的门槛**：能建出正确反投影的拿 0.98+，建不出的拿 0。中间没有梯度。

## 六、现在的判断和下一步

把上面这件事说完整：**二值门槛不必然是坏事，取决于这个门槛卡在哪里。**

平台希望通过率落在 1%~20%，因为低通过率信息量最高。如果"能不能自己推出这个反投影"本身就足够难，只有强模型做得到，那么二值门槛给出的通过率恰好就是想要的，题目成立。如果大部分模型都能做到，那这道题就没有区分能力。

**而这个数目前没有人知道。** 唯一的盲测样本是上面那一次，而它失败的那个原因在新规则下已经不算失败了——等于连这一个样本都作废了。

所以下一步不是继续加难度，而是**先在当前数据上跑几次盲测拿到通过率**。数据是现成的，成本几乎为零，而它决定后面所有的选择：

- 如果通过率已经很低，题目就位，不要再动；
- 如果通过率偏高，需要补一条有梯度的能力轴。目前有实测依据的候选是**半透明 alpha**——现有版本假设贴图 alpha 只有 0 和 255，这条假设正是让题目变简单的那一条（它保证了"最上层不透明的部件完全决定该像素"，把多层混合的解混问题降级成了单张贴图的一次采样）。在真实美术资产上试跑时，同一个 agent 因为套用这条假设，只利用了可用信息的 62.9%，而在它自己接受的那部分上准确率是 0.9907。这说明"能利用多少信息"是一条连续的、可测的、生产上真实存在的能力差异。

在拿到通过率之前讨论要不要加，是在没有数据的情况下猜。

## 附：这次 review 发现的几个具体问题

不影响上面的结论，但发布前应该处理。

**1. 目标皮肤生成器的默认值指向了已废弃的实现。** 生成器现在支持两种目标场：旧的解析式（三角函数叠加）和新的带限噪声。旧的那种存在一个严重问题——它每个通道只有 5 个自由度，**用整张贴图上任意 8 个像素做最小二乘拟合，就能把整页还原到 0.34/255 的误差**（基线是 45/255）。也就是说候选人可以跳过整个重建问题。新的带限噪声修掉了这一点。但代码里读取配置时写的是 `spec.get("target_generator", "legacy_periodic_v1")`——**默认值仍然是有漏洞的那个**。将来新增 case 如果忘了写这个字段，会静默退回可被利用的版本。建议把默认值改成安全的那个，或者直接删掉旧实现。

**2. 判分需要的掩码文件只存在于导出目录。** 判分脚本从 `<private>/observable_masks/` 读取可信掩码，但生成器把它放在了 `generated/exports/test_files/.../hidden/observable_masks`，而 `generated/<case>/private/hidden/` 下没有。直接按 `private` 目录调用判分脚本会失败。不影响正式流程（正式流程用的是导出目录），但会绊到任何想在本地复现的人。

**3. 原皮肤 S0 仍然是解析式生成的。** 它本身是低信息量的（每页只有 32 种颜色），这是有意设计——防止贴图颜色变成一种隐式的坐标编码，那样候选人可以靠比对颜色反查位置，绕过整个几何反投影。但既然目标皮肤已经换成带限噪声了，S0 也一起换过去更稳妥，成本很低。
